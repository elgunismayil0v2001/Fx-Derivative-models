# Fuzzing and robustness checks

The library takes numbers from outside (configuration files, market data, trade sizes). Whatever it is given,
it must either refuse with an error or return a result that is finite and obeys the model's own invariants.
It must never crash, hang, return NaN or infinity as a success, or return a finite number that breaks
no-arbitrage. This page describes how that is checked and how to run and extend it.

## What a target checks

A fuzz target is a function from a byte string to a verdict (`tests/fuzz/fuzz_targets.hpp`,
`tests/fuzz/fuzz_config_target.hpp`). It builds model inputs from the bytes, calls the library and returns an
empty string, or a description of the violated invariant. A refusal (an `Error`) is always acceptable;
only a *successful* result is checked.

| Target | Inputs decoded from the bytes | Invariants checked on success |
|---|---|---|
| `vanilla` | spot, rates, expiry, volatility, strike | price inside the no-arbitrage bounds; Greeks finite; put-call parity (1e-8); implied volatility reprices the option (1e-7) |
| `barrier` | market, volatility, strike, barrier, direction | knock-in and knock-out prices in [0, discounted spot + strike]; in-out parity (1e-6 of scale); touch probability in [0, 1]; one-touch + no-touch = discount factor |
| `delta` | spot, rates, expiry, volatility, delta | strike from delta, then delta at that strike, returns the delta (1e-6), when the inputs are in a range where the round trip is well conditioned |
| `risk` | P&L scenarios, mean, sd, confidence level | VaR and ES finite, ES >= VaR, VaR <= worst loss; backtest p-values in [0, 1] |
| `credit` | market, trades, exposure dates, path count | simulated values finite; EE >= 0; 0 <= PFE <= peak; CVA finite, >= 0, decreasing in the recovery rate and proportional to 1 - R |
| `sha256` | any bytes | 64 lower-case hex characters, deterministic, changes when a byte is appended or a bit flipped |
| `price_config` | a configuration document | never throws; a refusal carries a message; the verdict is deterministic; an accepted document satisfies its own limits |

The first byte of the input chooses the mode: even bytes feed *wild* raw doubles (NaN, infinity, denormals,
1e300, negative zero all appear), odd bytes feed *sane* values scaled into realistic ranges so that the
numerical code, not only the validation, is exercised.

## Two ways to run the same targets

1. **Replay test (every build).** `fxval_fuzz_replay_tests` is an ordinary GoogleTest executable and part of
   `ctest`. For each target it runs the seed corpus (`tests/fuzz/corpus/<target>/`), every saved regression
   (`tests/fuzz/regressions/<target>/`), a fixed number of seeded mutations of the seeds (bit flips, byte
   changes, insertions, deletions, truncation, splicing, overwriting eight bytes with an "interesting" double,
   byte runs) and random inputs. It is deterministic (a fixed seed per target, a fixed hash, no clock), so
   a failure reproduces on any machine, and it runs under AddressSanitizer and UBSan in the sanitizer jobs.
   It also asserts that a minimum share of the inputs get past input validation, so a target cannot go
   quietly vacuous.
   `FXVAL_FUZZ_SCALE=N` multiplies the iteration counts for a deeper one-off run:
   `FXVAL_FUZZ_SCALE=100 build/release/tests/fxval_fuzz_replay_tests`.
2. **libFuzzer (CI, coverage-guided).** `tests/fuzz/fuzz_<target>.cpp` are libFuzzer entry points. They need
   clang with the fuzzer runtime:

   ```sh
   cmake -S . -B build/fuzz -G Ninja -DCMAKE_BUILD_TYPE=RelWithDebInfo \
     -DCMAKE_CXX_COMPILER=clang++-18 -DFXVAL_BUILD_FUZZERS=ON \
     -DCMAKE_CXX_FLAGS="-fsanitize=fuzzer-no-link,address,undefined -fno-omit-frame-pointer"
   cmake --build build/fuzz --target fxval_fuzz_vanilla   # and the other targets
   scripts/run_fuzzers.sh build/fuzz/tests 60              # 60 s per target
   ```

   The `fuzz` job in `.github/workflows/ci.yml` runs 30 s per target on every push; `nightly.yml` runs 15 minutes.
   A crash fails the job and uploads the input.

## When a target finds something

1. Reproduce: the replay test prints the failing input as hex; a libFuzzer crash leaves a `crash-*` file.
2. Decide whether it is a library bug or an invariant that is too strict. Both happen. Document the decision.
3. Save the input as a file under `tests/fuzz/regressions/<target>/` (a descriptive name such as
   `f23_normal_overflow_0.bin`). It is replayed in every build from then on.
4. For a library bug, fix it and add a unit test that states the new behaviour in plain numbers. Record a
   finding in `docs/validation_report.md` section 6.

Seeds are generated by `tests/fuzz/make_seeds.py` (deterministic, no dependencies). Re-run it after a change to
the byte layout of a target.

## What was found

The first deep runs (20x to 1000x the default iteration counts, release and AddressSanitizer plus UBSan)
found three weaknesses, all fixed and pinned by regression inputs and unit tests: F-22 (barrier prices that
were finite but wrong for a volatility so small that the closed form loses all precision), F-23 (VaR and ES
returning an infinite value as a success when the P&L scale overflows) and F-24 (exposure simulation returning NaN
for exposure dates far beyond the supported horizon). See section 6 of the validation report.

## What this does not show

* The libFuzzer runtime was not available in the authoring environment. The seven entry points were
  compiled with g++ against a small stub driver and run on every seed and regression (no abort), which shows
  that they build, link and accept the corpus; no coverage-guided search was run by the author. The `fuzz` CI job ran once (30 seconds per
  target, no crash); the long runs of `nightly.yml` have not run yet (L-33).
* The invariants are chosen by the author. A model that is wrong in a way no listed invariant sees will pass.
* Passing a deep run is not a proof. It means that the chosen inputs did not find a violation.

## Mutation check

`scripts/mutation_check.py` replays recorded mutants for the market-risk, credit and hardening code (the earlier hand mutation checks are described in `docs/test_catalogue.md`): it
copies the repository, plants one recorded change at a time (`scripts/mutants/*.json`), builds, runs `ctest` and
reports each change as killed, surviving or not compiling. A pattern that no longer matches exactly once is reported as stale. It
runs nightly in CI (`nightly.yml`), and by hand:

```sh
python3 scripts/mutation_check.py scripts/mutants/credit.json --jobs 4
python3 scripts/mutation_check.py scripts/mutants/*.json --only 0 1 2
```
